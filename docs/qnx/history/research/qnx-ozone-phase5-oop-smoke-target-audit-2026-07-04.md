# QNX Ozone Phase 5 — Out-of-Process GPU Smoke Target Audit

**Date:** 2026-07-04
**Scope:** Read-only audit; no build, no QEMU runs.

## Key Finding Before Comparing Candidates

**`ozone_demo` does NOT spawn a GPU process.** The completed bounded smoke
(`docs/qnx/history/research/qnx-ozone-phase5-demo-render-surface-2026-07-03.md`)
used `params.single_process = true` in `ui/ozone/demo/ozone_demo.cc:65`:

```cpp
params.single_process = true;
ui::OzonePlatform::InitializeForUI(params);
// ...
ui::OzonePlatform::InitializeForGPU(params);
```

Both `InitializeForUI` and `InitializeForGPU` run in the same process;
no `--ozone-platform=qnx` flag, `--in-process-gpu`, or runtime choice changes
this. Chromium's `content/app/content_main_runner_impl.cc:524` skips GPU
process launch when `single_process || --in-process-gpu` is set. Therefore:

- **ozone_demo smoke = in-process GPU only**
- **`QnxGpuPlatformSupportHost::OnGpuServiceLaunched` is never called**
- **`QnxGpuService.Initialize` is never called**
- The software-canvas screenshot proves QNX Ozone UI startup only, not OOP GPU.

## 1. Candidates Compared

### `ozone_demo` (ui/ozone/demo:ozone_demo)

- **Launches separate GPU process:** ❌ No — `single_process=true`
- **Reaches `OnGpuServiceLaunched`:** ❌ No
- **Reaches `QnxGpuService.Initialize`:** ❌ No
- **Binary scope:** Smallest (~843 object files for the ozone lib). Not a GPU
  OOP exercise. Disqualified as next OOP smoke target.
- **Source:** `ui/ozone/demo/ozone_demo.cc`

### `content_shell` (content/shell:content_shell)

- **Launches separate GPU process:** ✅ Yes — `ShellMainDelegate` uses standard
  `ContentClient`/`BrowserMainRunner` with no `--in-process-gpu`.
  `content/app/content_main_runner_impl.cc:524`: GPU process spawned unless
  `single_process` or `--in-process-gpu` is set.
- **Reaches `OnGpuServiceLaunched`:** ✅ Yes — through `VizMainImpl` →
  `GpuHostImpl::Initialize` → `GpuPlatformSupportHost::OnGpuServiceLaunched`.
  `components/viz/host/gpu_host_impl.cc:450` calls it.
- **Reaches `QnxGpuService.Initialize`:** ✅ Yes — `OnGpuServiceLaunched` binds
  `gpu_service_remote_` and calls `QnxGpuService::Initialize(host_remote)`,
  which fires `AttachWidget` → `SubmitTestFrameForWidget` (see
  `qnx_gpu_service.cc`).
- **Binary scope:** Large (~78 833 total targets in a full CEF tree). Previous
  attempt (`out/qnx_phase5_oop_smoke/`) stopped at `mock_navigation_throttle_registry.h`
  signature drift (`AddThrottle` override mismatch), which is a pre-existing
  Chromium issue unrelated to QNX Ozone.
- **Source:** `content/shell/app/shell_main.cc` → `ShellMainDelegate`

### `cefsimple` (cef:cefsimple)

- **Launches separate GPU process:** ✅ Yes — full CEF browser, identical
  process model to Chromium browser.
- **Reaches `OnGpuServiceLaunched`:** ✅ Yes
- **Reaches `QnxGpuService.Initialize`:** ✅ Yes
- **Binary scope:** Much larger than `content_shell` (full CEF app bundle, not
  a single binary target). Not a next step.
- **Source:** `cef/tests/cefsimple/`

### `gpu_unittests` (gpu:gpu_unittests)

- **Launches separate GPU process:** ❌ No — pure in-process unit test; no
  GPU process spawns. Uses `content::RunGpuTests` in a single process.
- **Reaches `OnGpuServiceLaunched`:** ❌ No (only `OzoneGpuTestHelper` calls
  it, but the test executable is the GPU process itself, not a client).
- **Disqualified as smoke target** for OOP validation.

### `gpu_benchmark` / other GPU IPC targets

- `gpu/gpu_benchmark` is a browser-based benchmarking extension, not a
  standalone executable that spawns GPU processes.
- No Chromium standalone binary smaller than `content_shell` exercises the
  full GPU service launch path.

## 2. OOP GPU Process Launch Analysis

For a target to exercise `QnxGpuPlatformSupportHost::OnGpuServiceLaunched`
and `QnxGpuService::Initialize`, it must:

1. Run as the browser process (not GPU process).
2. Not set `single_process` or `--in-process-gpu`.
3. Initialize Ozone UI with `--ozone-platform=qnx`.
4. Chromium's `VizMainImpl`/`GpuHostImpl` must spawn the GPU process.

**`content/shell`** satisfies all four. `ozone_demo` violates rule 1 (it never
sets up the GPU service launch bridge at all).

---

## 3. Recommendation

**`content/shell:content_shell`** is the only viable OOP smoke target found — there is no smaller Chromium executable that exercises the GPU service launch path.

The previous build failure (`mock_navigation_throttle_registry.h` signature drift)
is a pre-existing Chromium content/test layer mismatch, not a QNX Ozone blocker.
It is fixable independently.

**Important:** `../out/qnx_release` (relative to this cwd) is regenerated by
`cef_create_projects_qnx.sh`. Until the tree is regenerated,
`../out/qnx_release` will not contain the newly committed Phase 5 Ozone files.
Always run `cef_create_projects_qnx.sh` before building in `../out/qnx_release`,
or use a deliberately prepared out dir that already has the QNX Ozone source
files applied.

**If approved**, rebuild with constrained parallelism:

```bash
cd /home/yuta/chromium/src/cef
./tools/cef_create_projects_qnx.sh --build-type Release \
  --qnx-sdp-root /home/yuta/qnx800
# OR, to build just content_shell from an existing QNX tree:
QNX_HOST=/home/yuta/qnx800/host/linux/x86_64 \
QNX_TARGET=/home/yuta/qnx800/target/qnx \
  ninja -C ../out/qnx_release -j2 content/shell:content_shell
```

Then run:

```bash
BUILD_DIR=../out/qnx_release \
  ./tools/qnx_run.sh --virgl --kill-existing --timeout 60 -- \
  ./content_shell --ozone-platform=qnx --no-sandbox \
  >/tmp/content_shell_qnx.out 2>&1 & \
  sleep 15; kill %1 2>/dev/null; cat /tmp/content_shell_qnx.out
```

**Do not build without explicit approval.** The `content_shell` target is
large; constrained `-j2` parallelism is required per plan safety rules.

## 5. Risks and Stop Conditions

### Machine stability

- **Broad Chromium builds** (`content_shell` has ~78 833 targets) load CPU/memory
  heavily. Previous instability was associated with this build class.
- **Stop condition:** If `ninja` or `clang` processes are observed consuming
  > 90% CPU for > 30 min without I/O, pause and report.
- **No new broad builds** until this smoke is complete and analyzed.

### Runtime risks (QEMU virgl)

- `content_shell --ozone-platform=qnx` will initialize the full browser UI
  and attempt to create a GPU-accelerated window. Expected EGL errors are
  non-fatal (fallback to software path).
- **Stop condition:** If QEMU hangs or exits non-zero before screenshot
  evidence, report and stop. If exit 139 (segfault) or exit 134 (SIGABRT),
  report immediately.
- **Do not** run `--ozone-platform=qnx` without `--no-sandbox` in QEMU;
  QNX user namespaces are not supported in the current QEMU configuration.

### Build risks

- The `mock_navigation_throttle_registry.h` fix (if needed) must be made in
  the root Chromium source, not CEF patches. It is outside the QNX Ozone scope.
  Report it as a pre-existing issue if it recurs.
- No changes to `patch/qnx/chromium/` are needed for this smoke target.
